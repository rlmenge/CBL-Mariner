# Azure Linux 4.0 kernel 6.18 config-policy audit

Scope: the 44 `kernel` overrides justified as “Align kernel 6.18 with its generated configuration” in the [4.0 checker policy](../scripts/ci/kernel/kernel-config-checker/kernel_config_checker/kernel_configs_json/azl4-os-required-kernel-configs.json#L3151). **Baseline: the actual 3.0 checker JSON on `upstream/3.0`, including its `kernel` overrides**, not just the 4.0 defaults. Compared policy expectations with the checked-in generated 6.18 configs for x86_64 and arm64. This is a **policy audit, not a decision to change the kernel configuration** or a comparison of the checkers' Python implementations.

**Bottom line:** Keep the overrides **as checker expectations for the existing `kernel` configs** until a kernel-config change is deliberately made. All 64 architecture-specific override values match the checked-in `kernel` configs **and change the effective 3.0 `kernel` policy**. Removing a conflicting override without changing/regenerating the kernel config would make the 4.0 checker expect the opposite value in 63 cases. The exception is arm64 `CONFIG_HSA_AMD_SVM=y`: it repeats the 4.0 default, but **reverses the 3.0 `kernel` override of `n`**. **Do not treat “matches generated config” as justification to abandon a security or product requirement.** Where the default is still intentional, fix the source config and regenerate first, then remove the override or promote the correct requirement to a shared default.

## What changed relative to the 3.0 policy

- The 3.0 policy has 367 default **symbol/architecture** entries; the 4.0 policy has 409. Of these, 57 are new, 15 were removed, and **none of the shared default values changed**. This is a comparison of policy JSON, not proof that either kernel generated the requested values.
- All **44 symbols and all 64 symbol/architecture pairs** in the table below have the **same defaults in 3.0 and 4.0**. For 63 pairs, the 4.0 `kernel` override reverses the inherited default. For the remaining arm64 `CONFIG_HSA_AMD_SVM`, 3.0 already overrode default `y` with `n`, and 4.0 now overrides it back to `y`.
- “Same defaults” means **same values**, not necessarily identical explanations: among these 44, the 3.0 ARC4 rationale said “Enable FIPS crypto configs and dependencies for arm64,” whereas the 4.0 rationale only links AB#22294; the QCom SMMU debug rationale was also reworded. Neither change independently resolves whether the requirement is still appropriate for 6.18.
- Consequently, the 4.0 values in these 44 rows differ from the **effective 3.0 `kernel` expectation in all 64 pairs**, not just 63. This is deliberately narrower than a full inventory of every 3.0-to-4.0 policy change. A change to the checker implementation or to the runtime behavior of a built kernel is **not** established by this comparison.

## FIPS requirements versus observed 6.18 settings

The supplied FIPS sources identify S1 as AB#22294 (baseline), S2 as AB#22390 (6.18), S3 as AB#22295 (DRBG evaluation), S4 as AB#18956 (LISA regression), S5 as AB#23422 (xxhash64 removal), S6/S7 as the 6.6/6.18 resolved configs, S8 as the July 9 boot findings, S9 as the AF_ALG versus IMA/EVM discussion, and S10 as AB#52297228 (secondary keyring). Those work items, the July 9 findings, and the final integrity-boundary decision were **not independently verified** here. The table below compares the user-provided targets to the checked-in [x86_64](../base/comps/kernel/6.18-x86_64-azl.config) and [arm64](../base/comps/kernel/6.18-aarch64-azl.config) `kernel` configs; it does not establish FIPS certification or successful boot.

| --- | --- | --- | --- |
| Core crypto/self-tests | `CONFIG_CRYPTO_FIPS=y`, `CONFIG_CRYPTO_SELFTESTS=y`; `CONFIG_CRYPTO_SELFTESTS_FULL=n` | Matches; FIPS name is `"Linux Kernel Cryptographic API"`, custom version is `n` | Preserve these checks. 6.6 used the different `CONFIG_CRYPTO_MANAGER_DISABLE_TESTS=n` / `CONFIG_CRYPTO_MANAGER_EXTRA_TESTS=n` symbols; do not carry obsolete assertions into 6.18. |
| Entropy and DRBG | Jitterentropy built in, `OSR=3`, `MEMSIZE_2=y`; DRBG implementations enabled | The listed settings match in the generated configs | Preserve the existing bundle. S3's possible HMAC-SHA512-only simplification is **provisional**, not grounds to drop CTR/HASH now. `CONFIG_CRYPTO_JITTERENTROPY_BUILTIN` is not a resolved setting. |

| Userspace AF_ALG boot path (S2/S9) | Six `CONFIG_CRYPTO_USER*` symbols built in **only if** the AF_ALG/libkcapi initramfs HMAC path is retained | `CONFIG_CRYPTO_USER`, `CONFIG_CRYPTO_USER_API`, and the HASH/SKCIPHER/RNG/AEAD API symbols are all `m` | **Conditional gap:** choose AF_ALG/HMAC or IMA/Secure Boot first. If retaining AF_ALG, make the necessary userspace API built in and verify boot; otherwise document the approved integrity replacement instead of enabling them reflexively. |

S2's built-in ECDSA target changes the recommendation for that override: it is a **configuration to fix**, not an acceptable permanent exception solely because it matches the generated config. S1's ARC4 `m` is *not* in the supplied 6.18 required-algorithms list; its `n` override is preferable until the baseline owner confirms the policy. The [checker](../scripts/ci/kernel/kernel-config-checker/kernel_config_checker/check_config.py#L76-L94) treats absent symbols as `n`; that comparison does not prove whether a symbol exists in 6.18 Kconfig or whether a built module is part of a validated cryptographic boundary.

For the companion signing/integrity policy supplied under S2/S6/S7/S9/S10, distinguish module signatures, trusted/revocation keyrings, lockdown, and integrity settings from direct FIPS-algorithm requirements. The proposed IMA appraisal settings are **conditional** on approving IMA as the integrity mechanism. The decision between AF_ALG/HMAC and IMA/Secure Boot is outstanding; neither these generated settings nor the checker alone can settle it.

## Caveats and next decisions

- These 44 entries target **`kernel`, not `kernel-hwe`**. The checked-in HWE generated configs currently have the same values for most rows, but HWE has its own overrides, and its checked-in generated files identify themselves as 6.18.45.1 while the HWE component source pin references 6.18.43.1. Do not use those copied/generated files as proof of the *built* HWE configuration without regeneration from the HWE source. On HWE x86_64, `CONFIG_CRYPTO_ECDSA=y`, unlike `kernel`'s `m`.
- The current HWE policy separately expects arm64 `CONFIG_ICE=n` and `CONFIG_ICE_SWITCHDEV=n` although the checked-in HWE generated config has `m` and `y`: [HWE overrides](../scripts/ci/kernel/kernel-config-checker/kernel_config_checker/kernel_configs_json/azl4-os-required-kernel-configs.json#L3671-L3690) vs [HWE config](../base/comps/kernel-hwe/6.18-aarch64-azl.config#L3806-L3808). It also inherits `CONFIG_CRYPTO_ARC4=m` from the default although the checked-in config disables it. These are separate HWE policy gaps, not reasons to copy all 44 `kernel` overrides to HWE.
- For every **review** row, make an explicit product/security decision against the original default's justification, update the source kernel config as needed, regenerate both architectures, then adjust policy. A checked-in `.config` proves the observed value, **not** that the required CVE fix exists or that FIPS validation has passed. No kernel or policy config was changed by this audit.
